# 代码库探索与首稿成本：36 次实测结果

已完成 9 次开发运行、27 次保留运行，全部使用新会话的 `gpt-6-astra/high`。本轮保留指引与源码教学示例的组合改动；不继续优化渲染器，也没有引入仓库索引工具。

最明显的改善是减少 Schema 返工。保留集 B 的 9 份首稿均触发 `schema/maxLength` 或 `schema/maxItems`；C 没有这类首稿错误，7/9 首稿直接合格，另外两份分别遇到布局与可读性问题。B/C 最终均 9/9 通过原生、共同、源码语义及实际截图评审。

保留集 C 相对 B，按三个任务等权计算：作者进程耗时下降 **10.04%（每任务中位数平均少 17.93 秒）**；计入 setup、最终机器复核和独立评审的工作耗时下降 **7.56%（少 19.37 秒）**。然而首稿前耗时上升 **18.20%（多 20.78 秒）**，JSON 后耗时下降 66.79%。这些阶段各取中位数，不能把中位数之差直接相加还原总差。

预登记的首要连续墙钟口径，从作者进程启动到最后独立验收结束，观测下降 19.85%。它混入评审排队、首次读源码准备和一次语义争议复核，不能解释成产品带来的 19.85% 提速。主动工作口径是补充指标，也受评审成本波动影响；不得用它替换首要口径后声称稳定端到端收益。**本轮观察到小样本改善趋势，未证明稳定总收益，也未攻克读库与首稿前的大头耗时。**

相对 main/A，没有可比较的合格端到端时延：A 在共同口径下 0/9 合格，其中 6 份有明确硬门失败、3 份缺少最终原生产物/验收证据。全部保留，不按零耗时计算。保留集 A 原生验收是 2 通过、4 失败、3 未知；共同验收是 6 失败、3 未知。原生政策差异必须与性能分开报告。

保留整个 Skill/示例组合：真实代码库的按需探索入口；事实与范围准备完成后直接写候选；根据结构选择示例；写作前查实际枚举、长度与来源约束；区分首稿自动路由与人工修过的展示样例；新增可物化的三文件 CLI“源码 → 证据 → 职责/关系 → JSON”教学例。

没有实施重型索引、全仓库压缩、额外符号服务、Git/helper 微优化、浏览器等待缩减、路由算法或门槛调整。重复阅读不是已证实的主要浪费；继续优化几秒机器阶段也没有优先级证据。详情见 [未采用方案](rejected-experiments.md)。

## 质量、适配与失败保留

最终每份合格 B/C 都经过冻结 B 的共同机器检查、源码主张逐条核对，以及 1440×900、1920×1080 的 light/dark 实际 PNG 查看。C 首稿的两次失败分别为 `composition/container-border-run` 与 `composition/desktop-readability`。A 的 12 份开发/保留首稿另用冻结 A 原生 validate 对精确快照与目标 SHA 统一补审，全部明确失败；6.88 秒补审单列，不是新作者样本，也不加入最终产物交付时延。

A 不支持 B 的 finalize 和持久化 provenance sidecar。其原生 `check` 不接受选项，`visual-check` 只使用实际支持的 `--json`；成功 deliver 的公开输出输入/产物 hash 与实际字节做外部绑定，不伪造 sidecar。原生 A 的纵向溢出与 B/C 可读滚动政策、共同边标签字体覆盖存在差异。B 对 A JSON 的重渲染仅是诊断，不能升级 A 的实际产物质量。原适配错误尝试和修正结果都保留。

sirv B 第三轮曾被初评判为两条边方向错误。独立第二评审结合源码、`precompute`/`compute on hit` 标签、views/cards 和其他组表达，确认这些箭头合法表达 header 结果进入索引/实时结果；调用方向的反向画法也可接受。原判、支持与反对证据、合并收据、额外耗时都保留，产物没有修改。未强制唯一画法，也未以“有源码行号”替代语义审查。

开发第一份 A 出现 sandbox 下 zsh heredoc 临时文件故障，原样计入预算；统一增加 TMPPREFIX 后复现通过。前三份开发运行 setup 未采集，保留 null；不能宣称完整总时延已知。失败、未知、未合格分别统计；作者进程 exit 0 本身从不等于合格交付。

B/C 本次样本未观察到语义或可读性回退，不能据此证明质量非劣。每任务三次、非独占主机、评审冷暖/争议成本、没有变体盲评和没有消融，均限制外推；不报告可靠 P95、显著性或大型真实仓库收益。
