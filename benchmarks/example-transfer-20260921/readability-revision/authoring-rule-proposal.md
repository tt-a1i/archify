# 架构总览的表达层级：待验证规则候选

这份候选来自一次用户明确要求的可读性重画。它没有进入正式 Skill，也没有在新的独立作者上验证性能。QuickLRU 已成为示教案例，不能再作为这条规则的未见测试集。

架构总览先回答谁负责决策、谁拥有状态、谁跨越边界。保留源码区分的角色、控制权、存储与外部回调。对同一对角色，不因每个 API 方法都有一次访问，就机械地各画一条平行线。

同一架构关系上的操作可以在总览中组合表达，具体条件、顺序、返回值和异常结果放在清楚标明的分组说明或专门流程中。每个移出的事实必须能指出新的可见位置；不能只用一个笼统标签掩盖分支。跨越不同所有权、协议、信任或持久化边界的关系仍需区分。读者要比较执行顺序时，使用相应的流程或时序表示。

几何校验失败仍按证据做局部修复。机器通过但读者无法理解时，应明确开启语义保持的表达重设计，核对旧图每个重要事实的去向，再重新做源码与视觉验收。不要把这种重画包装成一次局部路由修复，更不能将它混入已经冻结的性能试验。

本轮示教映射：

| 旧图逐操作关系 | 新图可见位置 |
|---|---|
| API 调用 | 调用方 → 控制器及引导说明 |
| 当前代覆盖、新增、阈值、新建 Map | 当前代访问关系；“写入”卡片 |
| 旧代轮换 | 旧代管理关系；“写入”卡片的完整顺序 |
| 当前代 get、旧代 get、晋升 | 两代访问关系；“读取”卡片 |
| has/peek 与过期检查及返回 | 有效期检查关系；“读取”“删除”卡片 |
| 到期回调、轮换回调 | 两条来源不同的回调关系；“删除”卡片 |
| delete 当前代、旧代、clear | 两代管理关系；“删除”卡片，保留计数与不通知条件 |

六个角色都保留，边从 16 条变成 6 条是本案例的结果，不是数量目标。评判标准仍是事实完整、关系易读及默认视口可用。
