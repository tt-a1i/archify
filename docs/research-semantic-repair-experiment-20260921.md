# 首稿探索：定向源码导航与局部路由修复（2026-09-21）

**本轮没有验证出同质量的端到端提速，两个原型保留为研究代码，暂不进入默认流程。** 六次完整作者任务中，五次通过机器交付门槛；按预先固定的语义标准和独立视觉评审，只有普通 Query 和普通 p-queue 两次完整合格。没有一对同时合格，不能据此计算同质量速度提升。

## 两项假设与原型

1. **定向符号导航。** 用 TypeScript Language Service 的真实静态绑定返回定义、引用和精确 AST 声明范围，区分实现与重载签名，并明确片段截断。它辅助定位，不能替代源码语义判断。原理与接口见 [TypeScript 官方文档](https://github.com/microsoft/TypeScript/wiki/Using-the-Language-Service-API)；实际原型与边界见 [导航研究](research-targeted-navigation-20260921.md)。
2. **诊断驱动的局部路由修复。** 仅处理单条自动连线的 `short-interior-segment` / `micro-segment`，保留所有非几何字段，不覆盖任何已有路由控制。最多三个固定候选，通过精确 SHA 绑定的完整 showcase 验证后才能返回 repaired，随后仍需完整 finalize。见 [路由研究](research-diagnostic-route-repair-20260921.md)。

导航初版在独立代码审查中暴露了 import 解析越出指定范围的问题。计时前已经修复：查询和返回位置限制在允许的根文件集合，过滤数量显式输出；TypeScript 仍可为绑定解析范围外依赖，固定编译配置不加载项目 tsconfig。审查和复测见 [原型审查](review-semantic-repair-prototypes-20260921.md)。

TypeScript 5.9.3 只安装在临时工具目录，禁用安装脚本，一次准备成本 **12.806 秒**，没有安装目标项目依赖。每次 CLI 都新建 Language Service/Program。最终配置 smoke 的完整进程约 **0.346 / 0.350 秒**；这只是入口可用性检查，不能当作出图收益，也不是冷文件系统测量。

## 方法与原始耗时

作者统一 **Terra/medium、新上下文、串行**，使用同一套正常 Skill、source-backed showcase finalize。顺序固定为 Ky B→N、Query N→B、p-queue R→B。B 为普通流程，N 增加一次必需的入口导航及可选后续查询，R 在适用诊断出现后才可调用局部修复。每次 600 秒、至多三次修复，不整轮重跑。

外部观察器保存每次观察到的候选字节变化；首稿为首个结构完整 JSON，不等于语义或视觉合格。表中结束时间来自原生单次作者任务，包含工具、修改和收尾；失败行表示停止时间，不是成功交付延迟。独立研究、源码克隆、准备、评审和事后截图不包含在作者时间里，另有整个研究轮次记录。

## 独立质量结果

第一次评审隐藏了条件标签、时间和工具使用情况，逐项检查源码、首末稿和 1440×900 light 截图；第二次独立复核核实争议条款、纠正措辞，并抽查通过项。首末稿在六个任务中均没有改变语义结论。

| 任务 | 关键结论 |
|---|---|
| Ky B / N | 均未表达 `throwHttpErrors` 与响应条件控制 HTTP 错误路径；B 还将 `beforeRetry` 的 stop 错连到 Final error，而实际返回 undefined。 |
| Query N | 已表达恢复状态的取消情况，不能说“完全没写取消”；但普通错误重抛及 cache success/error/settled 回调仍缺失，通用 updated-event 通知不能替代它们。 |
| Query B | 固定语义条款通过；普通错误、取消、回调与状态通知均有表达。 |
| p-queue R | 结算、容量释放和下一次准入有表达，但缺少冻结标准要求的 completed/error 终态事件。 |
| p-queue B | 固定语义条款通过；结算子标签及外部执行/取消边界足以表达所需含义。 |

所有五份已交付最终图的通用视口评审通过；部分连线文字偏小、辅助卡片位于首屏下方，属于整体阅读的限制，不是永久裁切证据。Ky N 没有交付图，视觉状态为 unavailable。首稿未过生产验证的情形也没有以事后截图冒充作者交付。

**标准敏感性必须保留。** throwHttpErrors 条件、命名回调、终态事件比宽泛的普通请求更具体，但已在出题前列入 required，不能事后改为 optional。第二轮复核明确记录这一点。较宽松口径或许会改变部分语义分数，却不会提供本轮未测得的同质量收益；尤其 p-queue 的工具仍然没有被调用。不要把本轮不合格简单等同于“图完全没价值”。

## 为什么没有运行预留修复对照

预先允许最多一对冻结候选修复，仅选择原任务顺序中第一个同时满足“独立语义完整、单条自动连线、只含支持的诊断、无路由控制”的首稿或最终稿：

- Ky N 首稿有两条目标边，不满足单边条件；最终稿只剩一条 15px 短段，但语义不合格。
- Query N 首稿只有单条短段，仍因语义缺失不合格。
- 两份语义合格候选首次就通过机器门槛，没有可比修复问题。

因此两次预留作者任务均未启动，没有改内容或放宽标准制造测试输入。路由工具只有小夹具的红转绿功能证据、旧 Polka 多种非路由失败时的安全拒绝证据；**真实同质量修复收益仍未知**。没有拿这些局部证据替代整体结论。

## 对大头开销的判断

六次首稿区间约 **135–198 秒**。发生修复的四次，首稿后又用了 **62–124 秒**；首次通过的两次仍有 24–36 秒验证与收尾。五次成功的最后一次完整 finalize 回执仅 **2.57–3.59 秒**。这支持继续优先验证减少首稿生成及诊断—修改往返的方法，而不是继续压缩几百毫秒的本地命令执行。

Query N 有 15 次公开工具调用，B 有 8 次。原生记录的累计 input_tokens 分别约 103 万和 49 万，包含大量重复缓存输入，不能当作唯一上下文大小或账单金额。导航没有在这个样本减少往返；原因仍可能包含模型策略与采样波动，不能只归咎于一个 0.35 秒查询。

公开工具调用/返回区间不是完整内部轨迹。异步命令可能跨出这些区间，剩余时间不能直接命名为思考、生成或网络延迟。原生任务事件未出现中止/服务错误，但这不证明没有隐藏 HTTP 重试。工具内部与最终机器回执、作者时间、语义验收分别报告。

## 取舍与下一项值得验证的假设

- 不把固定入口语义导航设成所有任务的必经步骤。其确定价值是准确定位和范围/歧义提示；这轮未证实完整出图更快。
- 不推广局部路由原型。它功能边界清楚，但适用范围窄，缺少真实合格输入上的配对修复证据。
- 下一项值得验证的是：**先固定面向用户问题的、可追溯的语义提纲，再降低写首稿几何和诊断修复所需的生成量与往返。** 这是新假设，不是本轮已证明的改进。应继续用正常请求、独立语义复核和完整交付时间对照，避免做成必须画尽全部源码的重流程。
