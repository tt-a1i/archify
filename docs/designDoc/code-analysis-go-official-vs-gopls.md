# Go 官方库与 gopls：维护和运行成本对照

2026-11-12。比较基线为 `197980b7`；gopls 对照为比较时工作树中的混合实验，现已另存。本报告保留切换前的研究数据。**后续已按官方库路线完成源码接入与缺陷修复**，当前状态见 [实现记录](code-analysis-go-official-implementation.md)。本报告不表示已合入或发布。

**研究结论：现阶段优先官方库路线，参考 gopls 的实现与边界处理；不继续把混合方案作为默认终点。** 理由是当前需求主要是批量事实提取，而我们最需要的接口实现证据和度量仍要自己组织。实验没有证明官方库能把一千多行缩成几十行；它证明了可以把部分工程职责交回上游，同时省掉 LSP 服务依赖。用户随后确认了这一方向，具体接入结果以实现记录为准。

## 1. 到底还要维护多少

原 Go helper 为 **1,181 行**；完成本轮功能对照的官方库原型为 **1,170 行**，JS 入口 **84 → 80 行**。均为含注释和空行的物理行数，不包含上游库、测试或实验 runner，不是维护工时估算。

最初原型为 1,147 行，补上官方模块解析、语言版本传递和加载失败处理后为 1,170 行。不能只报告中间阶段的删行数，也不能把保留的产品代码都算成“自研 Go 编译器”。

| 原型中仍由我们维护的部分 | 行数 | 为什么还在 |
| --- | ---: | --- |
| `go/packages` 调用、隔离目录、测试变体到产品包的映射、SDK 导出证据与错误处理 | 133 | 官方库返回包对象；捕获范围、来源与失败含义仍由产品定义 |
| `stdlib:false` 的捕获内 importer / `go/types` 检查入口 | 42 | `go/packages.LoadSyntax` 没有“不给标准库做类型解析”的开关；这条显式配置已有不同结果语义 |
| 源码筛选、排除原因和声明库存 | 107 | 保留平台/tags、坏文件隔离、指标库存及稳定排除理由；不能仅以已成功加载的包代替源码库存 |
| 坐标、函数范围、复杂度、嵌套、哈希、直接调用者 | 140 | Archify 的指标与证据口径，不是 Go 类型规则 |
| 重复声明、接收者唯一性、接口/具体方法的准入检查 | 94 | 错误代码中官方类型对象仍可能指向某个声明，不能自动视为可靠目标 |
| 接口实现证据组织 | 323 | 用官方 `types.Implements` / `NewMethodSet`，输出完整接口关系、`T` / `*T`、提升来源和未知范围 |
| 请求/数据结构、主遍历、调用结果投影、排序和 JSON 输出 | 331 | 产品数据契约与胶水代码；其中包括官方模块解析和调用对象到源码证据的映射 |
| **合计** | **1,170** | 这是本轮可工作的原型规模，不是最优下界 |

本轮实际交给上游的职责：默认模式的类型加载、SDK 导入实现、包/测试变体组装、模块语法解析及命名调用对象选择。删除了原手工测试包合并和 SDK `go list`/compiler-importer 装配；增加了公共库调用和必要的证据映射，故净行数变化很小。

默认模式直接消费 `packages.Load` 的类型对象，不再重复运行自己的类型检查器。`stdlib:false` 使用官方包元数据加一次 `go/types` 检查；这是同一官方库方案中的两种既有分析范围，没有 gopls 参与。这条兼容路径约 42 行，但相关配置、回归和文档也要继续维护。若未来取消该模式，应作为产品语义变更决定。

## 2. 具体参考了 gopls 什么

固定参考 `gopls/v0.21.1`，没有复制或导入其 internal 实现：

- [cache/load.go](https://github.com/golang/tools/blob/gopls/v0.21.1/gopls/internal/cache/load.go)：使用 `packages.Load`，区分加载范围和错误。本原型只实现一次性根模块快照，保留包级错误，不把“Load 没报错”当成源码全部有效。
- [golang/definition.go](https://github.com/golang/tools/blob/gopls/v0.21.1/gopls/internal/golang/definition.go)：选择适合文件的包变体，再以 AST/类型对象组织结果。原型从公共 `Package.ForTest` 取得测试身份，保留生产与测试的类型信息边界。
- [golang/implementation.go](https://github.com/golang/tools/blob/gopls/v0.21.1/gopls/internal/golang/implementation.go)：方法集查询和结果组织。我们只在捕获集合中调用官方类型关系 API，暂不建设它面向大型交互工作区的全局索引、session 和 snapshot 缓存。

使用的公开依赖是 [go/packages](https://pkg.go.dev/golang.org/x/tools/go/packages)、[typeutil.Callee](https://pkg.go.dev/golang.org/x/tools/go/types/typeutil#Callee)、`go/types`、`go/ast`、`go/parser` 和 `x/mod/modfile`。`Callee` 提供对象，不替代函数变量排除、错误声明检查和证据投影；不能改用会排除接口调用的 `StaticCallee` 来冒充等价结果。

**“官方库”不等于“全都随 Go SDK 附带”。** `go/*` 在标准库中；本原型还需锁定 `x/tools v0.52.0`、`x/mod v0.43.0`、`x/sync v0.24.0`。所选 `x/tools` 的 go.mod 要求 Go 1.26.0；本机使用 Go 1.26.2。不能继续照搬旧 helper 的 Go 1.18+ 支持承诺。

## 3. 行为验证与尚未解决的契约

- **26 / 26 通过，0 跳过**：复用基线全部 24 个 Go 测试，加模块 block/Go 字符串转义、声明语言版本两项边界测试。
- 实验副本有且仅有一项既有断言的语义调整：`standardLibrary.projectCommands` 从 `false` 改为 `true`，对应 schema 的常量也同步调整。原因是 `go list` 现在检查隔离的项目快照；原有绑定、指标、变更查询等断言没有放宽。原 schema 不接受这一变化，因此**不能声称已无缝兼容现行持久化契约**。
- 重放此前 28 份原始请求：27 份的选中文件、排除项、函数、调用、导入、接口边及覆盖说明一致。剩余一份含旧正则错误解析得到的 `module: "("`，新加载器明确拒绝；从原始合法 go.mod 重新走官方模块解析已通过新增测试。没有把这份异常回放伪报为通过。
- 三个真实项目的文件内容、函数指标/范围/哈希、导入边、接口边和调用语义逐项一致：共 **4,354 个调用、1,583 个已绑定目标**。比较对象键时忽略键顺序，保留 `receiverInterface`、`receiverPromotion`、`interfaceMethod` 和 `directCaller`。

| 项目 | 文件 / 函数 / 调用 | 已绑定目标 |
| --- | --- | ---: |
| chi v5.5.0 | 36 / 225 / 827 | 234 |
| Cobra v1.10.2 | 18 / 269 / 1,468 | 721 |
| x/mod v0.43.0 | 22 / 381 / 2,059 | 628 |

消融验证：强制所有模式都走 `LoadSyntax`，`stdlib:false` 的 SDK 接收者用例失败；去掉重复声明/方法歧义等准入保护，两个既有负例失败。保留这两部分。手工测试包合并和 SDK importer 删除后，存续路径通过上述行为验证。

本轮仍保持捕获根模块范围：不加载项目第三方依赖、replace、go.work、vendor、嵌套模块和 cgo，不执行项目程序、测试或生成器。默认加载器传递声明语言版本；捕获内兼容检查器仍未强制该版本。没有用本轮结果证明完整工程加载、大型工作区、多平台发布或所有错误代码均正确。

正式接入 B 前还需明确四项工作：新的加载/SDK 来源字段及 producer/revision 迁移；源码依赖或预编译 helper 的交付方式；超时/子进程清理与离线失败的发布级覆盖；支持的 SDK/目标平台矩阵。本轮原型复用了旧消费者做行为比较，尚未完成这些生产接入工作。

## 4. 运行成本实测

环境：macOS arm64、Go 1.26.2、Node 20.20.2；官方库版本如上，gopls v0.21.1。三个项目都关闭测试文件且不加载第三方依赖。每个方案先预热一次，再轮换顺序执行三次，取分析调用耗时中位数；没有并行跑其他测试。数据和采样方法见 [实验数据](code-analysis-go-official-vs-gopls-evidence.json)。

为避免把预编译优势误算成架构优势，主表两种自有 helper 均按每次 `go run` 比较；预编译结果另行记录在 JSON。

| 项目 | 旧官方标准库实现 | 新官方库原型 | 当前 gopls 混合原型 |
| --- | ---: | ---: | ---: |
| chi | 679 ms | 578 ms | 1,406 ms |
| Cobra | 725 ms | 338 ms | 1,355 ms |
| x/mod | 685 ms | 626 ms | 1,651 ms |

同一批的进程族 RSS 采样中位数，按项目顺序分别为：旧实现 **251 / 246 / 249 MiB**，官方库原型 **286 / 262 / 356 MiB**，混合原型 **500 / 500 / 570 MiB**。每约 50 ms 汇总父子进程 RSS，共享页可能重复计数，短峰可能漏采；这不是独占内存或内核峰值。官方库原型也并非所有资源都比旧实现少。

另外给每种方案独立的空 Go build cache，在 chi 上各测一次源码运行：旧实现 **8.41 s**、官方库 **9.82 s**、混合原型 **12.82 s**。模块下载缓存已准备，gopls 二进制已安装；未包含网络下载、gopls 安装或 OS 文件缓存冷却，不能称为完整首次安装耗时。

**混合原型仍有重复类型分析，以上不是“纯 gopls”的性能成绩。** 本轮只证明现有实验的实际代价。若选 A，必须先解决下述功能契约，再建立精简实现重新计时，不能从这里推算一个未经实现的纯 gopls 数字。

## 5. 安装、运行和升级：成本转移到哪里

| 成本 | B：官方库分析器 | A：gopls 单一语义来源 |
| --- | --- | --- |
| 用户安装 | 仍需 Go SDK。源码交付需下载固定工具模块并编译；预编译交付可由我们承担构建，但要做平台产物 | 仍需 Go SDK，另需兼容 gopls；可复用编辑器已有版本，但仍要定位和检验兼容性 |
| 实测可执行文件大小 | 原型约 **7.0 MiB**，旧 helper 约 6.9 MiB | 本机 gopls 约 **37.9 MiB** |
| 运行职责 | 捕获、一个批量 helper、go list/SDK 子进程、结果投影 | 捕获、LSP 初始化/能力协商、请求/通知、服务退出与超时清理、结果投影 |
| 我们跟随升级的对象 | Go SDK、固定 `x/tools` 等模块、加载结果和错误行为 | Go SDK、gopls 版本/设置/响应行为、LSP 客户端；能力不匹配时明确失败 |
| 回归仍归我们 | 当前证据、错误范围、历史结果和平台矩阵 | 同样需要；上游实现了查询并不等于我们的数据契约自动兼容 |
| 后续引用/诊断/重构 | 引用索引与范围、analyzer 驱动、诊断模型、编辑冲突等继续自建；不是零成本 | 上游已有公开能力，通常以接入和语义适配为主，是 A 的主要优势 |

文件大小为本机未裁剪二进制，不是安装包、源码缓存或总磁盘占用。预编译官方库 helper 只减少用户编译步骤，不能消除运行时 Go 包加载需求。两条路线都不应被描述成“用户只装 Go，剩下一切零成本”。

[gopls 官方支持说明](https://go.dev/gopls/#supported-go-versions)区分构建 gopls 的 Go、运行时 PATH 上的 Go 和被分析源码的 Go 版本；运行时支持政策跟随最近两个 Go 主版本。锁定版本便于复现，仍要安排后续升级验证；本轮没有对两个 gopls 版本做升级回归，不虚构年度维护工时。

A 的关键缺口仍是公开结果形状：`implementation` 返回位置列表，不能直接给出当前保存的完整 `valueSatisfies`、`pointerSatisfies` 和提升来源证据；复杂度/嵌套也不是它的公开指标。参见 [导航说明](https://go.dev/gopls/features/navigation#implementation)和固定版本源码。保留语法 AST 度量与“单一语义来源”并不冲突，但若为补齐接口证据再运行第二套类型检查，就回到了当前混合方案。

## 6. 选择建议

当前需求权重支持 **B**：保持官方库提供语法和类型规则，我们维护有限的批量查询与 Archify 证据。这不是因为它代码行数骤减，而是当前功能下 LSP 增加了运行边界，尚未替我们拿掉最重的产品证据逻辑。

`go/packages` 的价值主要是接管工程加载职责和未来扩展基础，不是本轮显著删行；若短期仍只做现有隔离单模块范围，现有标准库实现也没有因本轮数据而必须立即重写。可先采用公共模块解析、`typeutil.Callee` 等边界清晰的改进，再决定是否整体迁移加载器。

如果近期 roadmap 确定要做完整跨模块引用、持续诊断、rename/code action 等交互能力，A 的收益会明显增加，需要重新评估。原有 roadmap/额外能力清单见 [Go 替换与能力清单](code-analysis-go-gopls.md)。无论选择哪条，先决定现有证据契约，再比较同功能实现；不以删减能力或混合补齐来制造“完全替代”的结论。

原型、一次性研究脚本、逐次样本和失败日志保存在未随仓库分发的研究归档 `go-analysis-research-20261112/official-library-comparison/`。本报告与仓库 JSON 保存结论和哈希；原型及历史脚本未纳入本仓库，不能将摘要视作完整复现材料。
