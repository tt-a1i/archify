git restore 到底改了哪里？

长图

答

结论

git restore 先选恢复目标，再选内容来源：默认改工作区、取暂存区；加 --staged 后默认取 HEAD。显式的 --source 可以改来源。1

  1. 普通恢复会覆盖工作区内容，暂存区不变。
  2. --staged 只改暂存区，工作区不变。
  3. 同时指定 --staged --worktree 会改两个位置。

适用于一个已跟踪文件非冲突状态HEAD 已存在Git 2.50.0

1

三处内容如何流动？

HEAD 指向当前提交。暂存区保存准备提交的版本；工作区是磁盘上正在编辑的文件。箭头表示恢复时的复制方向，不代表提交或切换分支。1

图的结构
  • HEAD head
  • 暂存区 index
  • 工作区 work
  • head → index · --staged
  • index → work · 默认
  • head → work · --source=HEAD
2

四种命令分别改哪里？

下面四行各自独立执行，文件在来源中存在。命令只处理 file.txt；-- 后是路径。所有写法都不移动 HEAD。1

目的命令与结果
取回暂存版本git restore -- file.txt。暂存区 → 工作区；暂存区不变。
取消暂存git restore --staged -- file.txt。HEAD → 暂存区；工作区不变。
取回提交版本git restore --source=HEAD -- file.txt。HEAD → 工作区；暂存区不变。
两处都恢复git restore --staged --worktree -- file.txt。HEAD → 暂存区和工作区。

最后一行因为含 --staged，默认来源是 HEAD；也可显式加 --source=HEAD。注意：第二行保留工作区修改，第四行会覆盖它。1

3

覆盖前要知道什么？

恢复会覆盖目标

恢复工作区会丢弃目标文件中未暂存的内容；恢复暂存区会替换已暂存的内容。先保存想保留的改动。

若已跟踪路径在恢复来源中不存在，默认的非 overlay 模式会移除它，以匹配来源。--overlay 则不移除文件。1

这里假设暂存区没有冲突条目，且文件在稀疏检出范围内。冲突路径从暂存区恢复到工作区时，可能需要 --ours、--theirs 或 --merge；稀疏检出也会限制默认恢复范围。1
