P99 从 80 ms 涨到 600 ms，为什么平均值几乎没变？

长图

答

结论

因为只有最慢的 1%–2% 请求恶化到了 600 ms，其余 98% 仍保持 80 ms，大量正常请求把平均值摊平了。问题通常不在接口整体退化，而在排队争用、个别坏实例、下游偶发抖动或少数慢路径。排查时直接抓慢请求 trace，不要盯着全局平均值看。

  1. 平均值对长尾极不敏感：1000 个请求里有 15 个涨到 600 ms，平均值只涨 7.8 ms。
  2. 尾部尖刺说明慢请求有局部共性，往往集中在特定节点、下游或请求参数上。
  3. 排查顺序：先核对口径并抓慢请求 trace，再按维度切分，最后查变更与资源。

适用于数值为示意常见 Web 与微服务接口P99 按第 990/1000 个值计

1

为什么平均值看不出长尾变慢？

1000 个请求里，985 个耗时 80 ms、15 个耗时 600 ms：平均值 (985×80 + 15×600) / 1000 = 87.8 ms，只多出 7.8 ms。

但按耗时从快到慢排，第 990 个请求（P99）正好落进最后那 15 个慢请求里，直接跳到 600 ms。平均值会把少数卡顿摊平，所以线上告警必须盯住 P95 和 P99。

2

按什么顺序排查最快？

图的结构
  • 核对指标口径 confirm
  • 抽样慢请求 trace trace
  • 按实例与参数切分 dim
  • 对照发布与配置变更 change
  • 检查资源与锁争用 res
  • change → res
  • confirm → trace
  • dim → change
  • trace → dim
  1. 核对指标口径 ↗

    先看 P50 和 P95 是否同步上涨，排除监控聚合窗口或采样规则变动。

  2. 抽样慢请求 trace ↗

    抓至少 10 条耗时不少于 500 ms 的慢 trace，看时间花在排队、下游调用还是本机逻辑。

  3. 按实例与参数切分 ↗

    看慢请求是集中在某台机器、某个下游，还是带有相同接口参数或大请求体。

  4. 对照发布与配置变更 ↗

    把尖刺起点对齐部署记录、配置推送、特性开关和依赖升级时间点。

  5. 检查资源与锁争用 ↗

    排查连接池等待、线程池队列积压、GC 停顿、容器 CPU 限流和热点锁竞争。

3

常见根因怎么快速区分？

候选根因典型迹象确认方法
排队与资源争用慢 trace 里等待时间占大头，延迟随流量起伏最常见查连接池、线程池等待时长与队列深度
个别异常实例慢请求集中在少数一两个节点按实例分组看 P99，揪出离群机器
下游长尾变慢慢 trace 中单个下游 span 耗时占八成以上查数据库慢查询、行锁等待或缓存穿透
慢路径或大请求慢请求共享特定参数、租户或超大载荷对慢样本按路由、参数与响应大小聚类
GC 或运行时停顿尖刺呈周期性出现，且与 GC 日志时刻重合对齐 STW 暂停时长与接口延迟尖刺时刻
超时重试放大下游偶发超时后请求量突然成倍抬升对照下游入站 QPS 与重试计数曲线
