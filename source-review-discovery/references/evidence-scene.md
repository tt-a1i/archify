# 结构化证据画布

目的：让读者沿同一份输入看清不同处理路径、哪一步改变了数据、输出有什么差异，以及依据和未知。结构与布局固定，问题判断来自调查。所有业务事实仍在 `review.json`，scene 不是第二份报告。

## 交付过程

1. 先发布报告并追加已完成的隔离验证，再取得 `review_report.py digest --report review.json`。
2. 选择一个真实 finding，填写 scene，引用其节点、证据和验证用例。先保证解释成立，再选默认场景；能同时展示正常保留与异常遗漏的场景通常更有信息。
3. 执行下列命令。校验失败应纠正结构或返回原报告视图，不绕过校验。

```sh
python3 scripts/review_report.py validate --report review.json --scene scene.json
python3 scripts/review_report.py render --report review.json --scene scene.json --out runs/scene-v1/index.html
```

浏览器查看默认场景、切换对照场景、点击偏差节点检查源码及行号，确认窄屏无横向溢出。导出任务继续使用原报告的身份、状态、验收和复查流程。切换场景只读取记录，不执行产品代码。

## scene 字段契约

所有对象拒绝未列字段；必填字段不得省略。新画布使用整数 `schema_version: 2`；旧版 1 继续可用。

| 字段 | 内容与约束 |
|---|---|
| `report_digest` | 绑定完整报告的 digest；报告改变后重新核查再绑定。 |
| `finding_id` | 报告中的真实发现 ID。 |
| `input_node` | finding.graph 中的公共输入节点 ID。 |
| `lanes[]` | v2 每个分区含 `id`、`title`、`nodes:[节点ID]`、`output_node`、`measure`；output_node 必须在本区 nodes 内。v1 保留 process_node 代替 nodes，编译为两个节点。节点引用同一 finding；`measure={label,unit,actual_key}` 表示输出量及其验证字段。unit 可以为空。 |
| `scenarios[]` | 见下表，至少一个。 |
| `default_scenario` | 已声明场景的 ID；由问题内容决定，不固定为某个案例。 |
| `focus` | 节点 ID 到 `{evidence,start,end,highlight:[行号]}` 的映射。可为空；证据须属于该节点，选择范围和高亮不得超出采集摘录。 |

每个 scenario：

| 字段 | 内容与约束 |
|---|---|
| `id` / `title` | 唯一场景 ID / 读者能理解的名称。 |
| `kind` | `control`、`trigger` 或 `exploratory`。 |
| `input` | `{origin,groups,evidence}`。origin 为 `synthetic`（合成）、`observed`（观测）或 `hypothetical`（假设）。 |
| `input.groups[]` | `{label,fields:[{label,value,unit}]}`。value 是有限 JSON 标量；分组用于显示真实结构，数值与标签须核对输入依据。 |
| `input.evidence[]` | 本 finding 已关联的证据 ID，必须属于发现版本。假设输入可为空，其他类型不可为空。源码依据只证明合法形状，不证明某个值曾在线上出现。 |
| `states[]` | `{node,summary,basis,evidence}`。同一场景每个节点最多一条；basis 为 `source`、`inference`、`unknown`。未知可没有证据，其他必须引用。说明当前输入经过该节点时发生什么。 |
| `verification_case`（可选） | `{run,name}`，精确匹配当前 finding 的一个验证用例，kind 一致。输出直接读取其 `actual[measure.actual_key]`。没有此引用时输出显示“未验证”，不允许手填 observed/outputs。 |

## 布局与边界

v2 支持一个公共输入及多个分区，每区可以包含多个节点。输入与分区必须恰好覆盖 finding 的所有节点，每个节点只归属一处。所有连线直接来自原 graph.edges；分叉、汇合、回边和平行关系全部保留。分区只是阅读归组，不自动证明依赖或调用。v1 继续严格校验原先的“处理 → 输出”对照。用 `bundle` 将多个场景和同一份报告的目录全景连接起来；其事实图与任务身份保持不变。

画布复用固定版本的 Archify 原生查看器：平移、缩放、搜索、聚焦、路径检查、动态/静态切换、演示和图像导出由原生实现负责。节点的信息排布由审查适配层设计：输入展示分组字段和值；处理展示当前场景的变化说明、推导依据类型和源码位置；输出突出记录里的实际值、单位与验证来源。不能把所有信息缩成节点标题，也不能把完整源码堆进画布。标识符整体换行，完整说明在证据栏可读。

选择节点或关系会同步下方的源码证据；浮动面板中的“展开源码与证据”可直达摘录。手机默认按分区阅读完整说明，提供“展开交互画布”；“在画布中定位”先展开再定位。浮层分类使用真实审查角色，不让底层配色借用的 frontend/backend/security 类型泄漏成业务断言。

切换场景只改变输入说明、节点结果和证据解释，保留同一画布节点与相机位置。默认动态模式展示沿箭头的过程示意；尊重用户已选择的静态模式及系统减少动态效果偏好。动画不能表达未经记录的生产执行或实际失败次数。源码确认关系保持实线；推导和待核定关系保持虚线，详细依据仍分开标注。

循环先按强连通分组进行布局，原节点和边不合并或删除。高亮分别沿图向上游、下游遍历，不通过共享上游扩散到兄弟路径。高亮不是运行可达性或生产影响范围的证明。

图中标题、影响、反证、未知、建议和验收均读取报告。节点点击展示采集的源码；实线为源码关系，虚线为推导或未知，详情说明各边的含义。节点角色来自原发现；颜色不代表新增验证结论。

验证数字可以为 0，布尔值可以为 false；它们不同于“未验证”。页面显示的是历史隔离验证，不是生产轨迹；记录来源、限制、源码新鲜度和当前处理状态分别保留。同一 finding 有多个验证记录时，不沿用报告中聚合的新鲜度来断言单个记录仍有效，而显示需核定。

校验不能证明场景值与测试夹具一致，也不能证明源码推导正确。审查者必须核对输入夹具、契约和反证，不能因为 JSON 合法就升级结论。已复查的报告仍展示原问题过程，当前状态单独标注；新版本行为需要新证据。

## 最小化设计

只新增 scene 及统一适配器；不新增任务、问题身份、验证结果或业务状态机。不提供每例脚本或图插件系统。相机和选中属于临时阅读状态，不写回事实报告或修复任务。标准库校验器 `scripts/review_scene.py` 是字段和引用约束的可执行定义。

`scripts/review_native.py` 将已校验 scene 映射成原生 architecture 数据，保留每个节点和关系；循环先进行强连通分组再排列，关系不合并。原生布局拒绝碰撞等问题时停止渲染并报告原因，不删边来通过。当前生成 scene HTML 需要 Node.js；普通报告渲染和 scene 事实校验仍仅需 Python 标准库。生成后的 HTML 独立离线打开，无 CDN 请求。

Archify 的依赖文件位于 `assets/vendor/archify`，上游固定为 `a4065941f12be7967436261d9934784e381d423c`。`UPSTREAM.json` 记录来源及每个文件 SHA256；许可证、NOTICE、第三方声明和字体许可随文件保留。只复制 architecture 渲染所需的导入闭包及运行数据，没有修改上游文件。主题、相机、动画、搜索、图导出统一复用上游；我们仅保留事实绑定、布局适配、场景切换、证据与修复任务桥接。不要重新实现第二套相机和动画。
