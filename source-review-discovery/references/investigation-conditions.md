# 按实现选择调查条件

主提示词中的 A–H 与下列条目一一对应。按实际代码迹象读取相关条目，使用其中的工具路线、反证和验证方式继续调查。

来源与取舍见 [research-sources.md](research-sources.md)。以下是为本 skill 写的操作化条件，不是书籍原文，也不是经过校准的缺陷概率模型。

## A. 同一业务规则在多处独立实现

- **出现条件**：多个入口、消费者或适配器自行维护类似枚举、校验、计算或状态映射；修改一条规则可能影响多处。
- **要问**：这些实现是否承诺同一语义？有没有真实允许的输入，使不同入口产生冲突？同形代码是否其实服务不同政策或版本？
- **先查什么**：有重复迹象但位置不明时，`source_tools.py duplicates` 给双边位置；`--matching renamed` 可查一致改名后的相似片段。接着用 `rg` / Tree-sitter 读取完整定义、LSP 引用确认调用方；已有已知实例时，Semgrep 从准确匹配开始逐项放宽，再逐个核查。可用 `review_facts.py history` 查共同修改，记录窗口和分母。词法相似不保证业务等价，短样板和不同政策需要撤回或分开处理。
- **反证**：共享生成源、共同底层函数、明确版本隔离、不同业务契约、纯样板代码。共同提交可能只是格式化、迁移或打包发布。
- **验证**：按真实公共契约给两个原消费者相同输入，观察必须一致的字段；对不要求一致的字段不作断言。没有语义等价依据时保持设计疑问。
- **依据**：Fowler 的 code smell 原则；Tornhill 的复制代码与共同修改分析；variant-analysis 的逐步扩展方法。

## B. 模块边界没有隔离变化

- **出现条件**：调用者需要了解被调用模块的内部字段/调用顺序；多个模块一起变化；跨层依赖或循环导入值得进一步核查。
- **要问**：哪项内部变化会迫使哪些外部调用者跟着修改？边界承诺在哪里？大量依赖是否只是稳定的公共接口？移除一个疑似多余抽象后，复杂性会消失，还是转移到多个调用者？先核对现有领域约定和 ADR 的取舍。
- **先查什么**：`architecture.mjs` 生成底图，`review_facts.py dependencies` 取进入/离开边界的具体文件行号；`history` 和 `source_tools.py metrics` 作为可选优先级资料；再用符号引用读实际调用。不将 import 当作运行时调用。复杂度用于选择分支多的入口，不据阈值推断职责过多；Lizard 返回空值的指标/位置必须另核。
- **反证**：公共协议层、依赖注入或生成代码、允许的插件扩展点、类型专用依赖、稳定且高内聚的模块。未提取到 HTTP/消息边不表示没有跨服务耦合。
- **验证**：选择一个符合现有需求的具体变化，在只读调查中列出必要改动位置和共同原因；有授权才做隔离修改实验。不能只凭“依赖多”要求拆模块。
- **依据**：Ousterhout 的变化放大、认知负担与隐蔽依赖；Tornhill 的变化耦合；Matt Pocock 的架构调查和抽象删除追问。

## C. 生产者与消费者理解的契约不同

- **出现条件**：序列化、枚举、版本映射、结果分组、默认值、空值、多视图投影。
- **要问**：生产者可能产生的值，消费者是否覆盖？转换保留了哪些语义、身份、版本及未知状态？默认分支是否把“未知”解释成成功或失败？
- **先查什么**：读取实际生产者和所有相关消费者；用 Tree-sitter/Semgrep 定位映射，LSP 查引用，Joern 在已支持的语言路径中追踪丢失或转换的值。把发出集合和接受集合放对照表，区分源码提取与人工解释。
- **反证**：上游有约束、协议版本协商、规范化保证、未知值有显式保留、消费者本来只接受受限子集。名字相同不证明同一业务对象。
- **验证**：契约允许的值、一个正常对照、缺失/未知值；真实编解码、序列化或消费函数。只有契约保证无损时才要求往返等价。
- **依据**：property-based-testing 的往返、不变量与参照关系；本项目对跨模块业务契约的操作化推导。

## D. 副作用与确认之间有失败窗口

- **出现条件**：提交/保存后还要通知、生成答复、更新展示；超时后重试；一次操作写两个系统。
- **要问**：在每个外部交接前后失败，哪些事实已保存，哪些只存在内存？超时是否只能说明结果未知？重试沿用哪个业务身份？返回失败会不会被错误解释为没发生副作用？
- **先查什么**：沿入口 → 写入 → 返回/异常 → 重试/查询追踪；检查幂等键、唯一约束、事务范围、outbox/补偿及锁定依赖源码。Joern CFG 只辅助局部执行顺序，跨服务原子性仍须核对真实实现。
- **反证**：提交前校验、覆盖整个操作的事务、持久幂等回执、原子唯一键、可查状态、明确可补偿的业务动作。发现一个保护后核对它覆盖的具体失败窗口。
- **验证**：可隔离时在真实副作用完成后的边界注入失败，再重放同一业务请求；需真实重启/并发/远端契约时标 deferred，不能用绕开写入的桩证明。
- **依据**：DDIA 作者关于异步系统和延迟写入的论述；Release It! 的外部集成失败。

## E. 状态、所有权或时序被混用

- **出现条件**：取消、恢复、过期回调、异步完成、多个状态源、排序取“最新”、租约/版本号。
- **要问**：谁拥有状态？任务状态、审批状态和业务对象状态能否互相代替？旧执行/旧版本能否覆盖新状态？取消响应是否等于业务作业已停止？
- **先查什么**：所有状态写入点、对象 ID、执行 ID、版本比较与读取投影；LSP 引用查写入消费者；结构工具缩小范围，源码核对允许的迁移和分支条件能否同时成立。
- **反证**：单一串行写者、CAS、版本保护、fencing、终态不回退约束；时间戳排序只有在相应顺序保证成立时才足够。
- **验证**：从已证实的契约推导状态机性质，例如旧版本回调不能改变新版本对象。用受控事件顺序测原状态写入代码；不要从业务名称凭空发明允许的迁移。
- **依据**：DDIA 作者对暂停进程和过期写入的分析；property-based-testing 的状态不变量。

## F. 数值的含义在转换中丢失

- **出现条件**：单位、比例、最大/平均、取整、展示格式、多个来源或归一化结果。
- **要问**：参与比较的是同一物理量、统计口径、单位和版本吗？展示舍入是否进入业务判据？未知/冲突有没有被当成零或合格？
- **先查什么**：标明值的来源、量纲、尺度、统计含义、转换和最终用途；已有 Tree-sitter、引用和数据流查询辅助追踪。表格记录在审查产物，不给目标代码自动加注释，也不靠字段名猜单位。
- **反证**：统一规范化、显式单位转换、准确 Decimal 运算、只在展示末端舍入、来源冲突时拒绝判定。
- **验证**：真实边界值及正常对照；只有契约明确时才要求单位转换前后判定一致、规范化幂等、精度误差有界。生成器不得把非法输入伪装成生产输入。
- **依据**：dimensional-analysis 的量纲追踪；property-based-testing 的代数性质。统计口径与来源一致性是本项目补充。

## G. 外部等待或资源没有明确上限/释放路径

- **出现条件**：网络调用、队列、重试、池化资源、无限集合、后台任务、连接/文件/锁生命周期。
- **要问**：慢依赖会占用什么？超时和取消是否传到实际工作？重试层叠后总次数/总期限是多少？异常路径谁释放资源？
- **先查什么**：搜索入口与客户端构造配置，读锁定依赖的默认行为；用调用/控制流定位等待和清理。查全局超时、作用域管理、退避、背压、队列容量，不能仅凭当前函数没传 timeout 下结论。
- **反证**：上层总截止时间、框架取消传播、RAII/with/finally、全局客户端配置、天然有界输入及隔离池。
- **验证**：在本地受控依赖中模拟立即失败、慢响应和取消；保留真实超时/清理逻辑。资源耗尽与性能结论需相关负载依据，纯源码先报告条件和容量未知。
- **依据**：Release It! 的集成点与慢失败分析；sharp-edges 对默认值含义的追问。

## H. 接口把正确使用所需的隐藏规则交给调用者

- **出现条件**：相同基础类型表示不同身份；布尔组合控制互斥行为；必须按特定顺序调用；0/空值具有特殊意义。
- **要问**：正确用法要记住哪些代码之外的约束？有真实调用者违反了吗？输入校验和类型能否表达这个约束？
- **先查什么**：读取公开签名、构造器、默认值和现有调用者；按引用区分对象身份，找实际误用后再用 Semgrep 查同类实例。
- **反证**：语义类型、构造器校验、受控内部接口、明确且强制的生命周期。易误用只是设计风险，不能假设有人已误用。
- **验证**：只有真实公开契约允许的输入/调用序列进入验证；发现前置条件禁止某用法时，回查是否存在绕过路径。
- **依据**：Ousterhout 的隐蔽依赖；sharp-edges 的 API 误用检查。这里扩展到普通业务接口，不能把其安全结论直接套用。

## 怎样判断效率和质量是否提高

以相同源码版本、入口和查询预算比较旧流程与本流程；首轮报告冻结前不读取故障记录、答案集、修复 diff 或现成测试结果，由评估者保留答案。后续验证与首轮发现分开记录。记录独立核定的问题、误报、撤回、关键未知、有效查询数、耗时和工具开销。新增查询应消除具体未知。已知案例只作回归验证，不算盲测新发现。不要用 LLM 自评概率、多数投票或工具命中数量代替效果评估。
