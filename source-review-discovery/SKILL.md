# 从源码发现问题

从真实实现回答：哪里可能违反现有契约，哪里让一次合理修改扩散到多处，哪些判断还缺证据。不要预设问题数量、套用历史案例的结论，或把设计偏好当作缺陷。发现阶段只读源码；发现后，在授权范围内做隔离的最小验证。用户没有提供故障、目标清单或测试结果时，仍可从实现中的契约与交接开始。

交付遵循 [输出与复查约定](references/output.md)，创建版本化 JSON 与离线 HTML。工具负责采集摘录、校验引用和生成图表；Agent 负责问题发现、论证及复查判断。不要只交自由格式 Markdown。

## 从用户范围建立上下文

用户指定模块或功能时，沿它的入口和相关消费者调查；没有指定时，从公开入口、状态写入、多消费者转换和外部交接选择起点，说明实际范围。Git 修改热点可帮助排序，缺少历史不阻塞调查。只有预期业务行为会改变结论且源码无法判断时，才留下明确的需求问题；继续其他可核查路径。

固定源码及依赖版本。读取输入、输出、持久对象、状态所有者和必要上下游。类型约束、真实调用、领域文档及 ADR 提供契约和设计背景；名称、注释和测试断言也可能有误。区分明确承诺、实现推断和未知要求。跨仓跟随锁定依赖，不拼接不同时间的实现。

按 [调查工作目录](references/investigation-workspace.md) 在源码之外初始化或恢复审查目录。先查询 `capabilities`，确认目标语言的已安装、可用和实测能力；已有目录先读取问题及相关证据的新鲜度。手填 revision 只是标签，文件散列与实际覆盖另行核查。

## 按代码迹象选择调查方向

下表用于选择方向，不要求逐项扫描或各报一个问题。出现相关迹象时，读取 [调查条件](references/investigation-conditions.md) 对应条目的工具路线、反证和验证方式；新的证据可以改变方向。

| 代码迹象 | 首先要核查的问题 |
|---|---|
| A. 相似规则在多个入口独立实现 | 是否承诺同一语义，一次政策变化是否需要多处同步？ |
| B. 调用者依赖内部细节，修改跨越多个模块 | 边界是否隔离了变化；移除某层后复杂性会消失还是转移？ |
| C. 生产者、转换和消费者处理同一数据 | 合法值、身份、版本、空值和未知状态是否被正确保留？ |
| D. 写入或提交后仍有可能失败的步骤 | 已发生什么副作用，确认失败后的查询和重试如何处理？ |
| E. 多个状态源、取消、恢复或异步回调 | 谁拥有状态，旧执行是否可能影响新对象或新版本？ |
| F. 数值经单位转换、聚合或展示舍入 | 最终判断使用的含义、口径、来源和精度是否一致？ |
| G. 外部等待、重试或资源占用 | 总期限、取消传播和异常释放由哪一层保证？ |
| H. 接口需要记住调用顺序或特殊参数含义 | 正确使用依赖哪些隐含前提，实际调用是否遵守？ |

长函数、重复外形、高依赖和共同修改只是调查信号。行为缺陷要论证合法触发及契约违反；维护性问题要说明一项具体改变为何传播、所需修改位置和实际代价；预期不明确时保留设计疑问。不要为维护性建议制造运行失败。书籍与现成 skill 的来源、适用边界见 [研究依据](references/research-sources.md)，只在需要追溯方法时读取。

## 用工具推进可反证的假设

每个候选保留简短记录：**观察 → 契约依据 → 触发前提 → 可疑路径及影响 → 支持与反对证据 → 关键未知 → 下一次查询**。先回答下一次查询能区分哪两种解释，再按 [工具说明](references/tools.md) 选择现有能力。一般从搜索/声明、引用和边界开始，必要时升级到控制/数据流；优先复用同版本结果，不为凑工具覆盖运行所有引擎。

采集时给 `source_tools.py` 加全局 `--workspace`，将观察、原生结果和输入身份留存。先读摘要，再用 `review_workspace.py view` 按页、路径、记录 ID 或原始 JSON Pointer 查询；不要为取下一页重跑扫描器。源码、配置或覆盖变化时重新核查适用性。查看一个位置的多项事实时用 `context --facet …` 按需组合声明与 LSP 查询；未支持的语义能力必须保留缺口。

需要继续查询的候选用 `question create/update` 保存支持、反证、具体未知和下一步，更新须绑定上一版 revision。结论被反证推翻就记录 withdrawn；尚无依据则保持 open/investigating/blocked。问题记录的 resolved 只表示这个调查问题已回答，不等于缺陷成立或修复完成。工具校验引用和版本，Agent 负责判断论证；不得把保存了问题当成新增 finding。

维护性调查优先复用多语言基础能力：`source_tools.py duplicates` 给重复片段候选，`metrics` 给函数指标。先核对范围中的生成文件、第三方包和声明文件；按需要明确排除并记录。读取 coverage、原始结果及不可靠字段，不能把高复杂度或复制命中直接变成发现。选少量与用户范围相关的候选，继续读完整实现、消费者与反证，再进入同一报告和最小验证流程。

沿生产者 → 转换 → 消费者，或入口 → 副作用 → 失败/返回 → 恢复追踪。核对分支条件能否同时成立。主动检查上游规范化、下游幂等/补偿、数据库约束、框架保障及其他公开查询。保护覆盖该路径时收窄或撤回；只在局部看不到保护，不能证明全系统缺失。确认根因后再渐进扩查同类实例，保留撤回理由。

符号/调用图只帮助定位，不能独立证明运行可达；模式匹配不能确认对象身份；工具空结果、失败或不支持不能解释为安全。合成输入须符合真实调用契约；接口未返回数据不等于数据丢失，提示词存在也不证明模型实际遵守或违反。

## 结论与停止

分别标明 **静态确认**（契约、可达前提、违反路径都有源码依据）、**条件风险**（关键外部/并发/调用条件未知）、**设计疑问**（预期要求不明）、**撤回**（存在反证）。严重度另列。不给这些标签编造概率。

每项问题说明触发条件、违反的依据、实际影响、具体文件与行号、已检查的保护及剩余未知。先有具体问题，再按共同原因提出最小共享改进；不得为了凑架构方案把不相关问题合并。

报告本轮检查的路径、未覆盖范围和工具缺口。静态审查不声称复现模型误答、现场超时或真实用户行为。当前材料无法解决的未知保留，继续其他路径；授权范围内的重要候选处理完后交付结论。

评估发现能力时，按 [调查条件中的评估约定](references/investigation-conditions.md#怎样判断效率和质量是否提高) 隔离答案和后续验证，历史回溯不得称为盲测。

## 可读报告与闭环

交付前按 [README](README.md) 配置需要的运行时。审查产物保存在仓库外或 `.source-review/`，不要把目标项目的报告、摘录、截图和验证输出混入 skill 实现提交。

需要系统全景时，先提取真实源码目录与 import 关系，再将问题的证据文件关联到模块；不能把几项问题的节点冒充整个系统。主视图按“系统 → 模块 → 问题 → 验证/证据”展开。没有发现标记不等于安全，静态 import 不等于运行调用、HTTP 或消息关系。工具覆盖按实际语言后端说明。

有底图时优先用 `review_report.py bundle --report review.json --scene scene.json --out NEW_DIR` 交付相互连接的全景和问题页；可重复 `--scene`。全景展示模块规模、关联问题和验证状态，点击模块查原始 import 与源码文件，再进入问题路径；返回保留阅读位置。未提供专门 scene 的问题仍保留通用证据入口。不要按样例另写网页，也不要把目录布局解释为调用流程。

先用用户、下游或维护者可核查的影响写标题，再解释发生条件、偏差位置和保护。维护性条目说明具体修改会涉及哪些位置，预期改进收益与已观察事实分开。内部字段、函数名、证明义务放源码详情。图按问题选择数据流对照、协议对照表、失败窗口或决策过程；箭头有明确含义，不能把并存或比较画成因果。

填写 draft 后用 scripts/review_report.py 的 publish 采集证据，再 render 生成 HTML。证据不足时显示具体缺口和下一次调查，不能用健康分或命中数替代论证。同时保留已查/未查范围和实际工具。

对“共同输入 → 各处理路径 → 输出差异”，优先使用 [结构化证据画布](references/evidence-scene.md)：生成绑定报告版本的 scene JSON，由固定版本的 Archify 原生查看器绘制；生成需要 Node.js，HTML 可离线打开。v2 每区可以有多个节点，保留分叉、汇合与回边；v1 仍兼容。节点及关系可选择查看证据，场景中的详细变化进入证据栏。运行输出只能引用已有验证记录，未验证显示未知。不要按案例编写 HTML/JS，不能为适配布局删除关系或新增未经论证的步骤。动效是过程示意，图遍历高亮不等于生产调用轨迹或已证实影响。

发现冻结后按 [最小验证与架构底图](references/verification.md) 判断验证是否足够小：保留真实源码函数、实际契约允许的触发输入及正常对照，隔离的依赖不得代替待证明的行为。记录执行代码、输入依据、源码散列、输出和验证边界。并发、重启、外部平台前提尚不清楚时保留待验证及难点；默认首页只展示已完成最小验证的发现，其他记录可主动展开。未复现不等于不存在，局部复现也不自动升级业务可达性。

用 task 导出绑定身份、版本、证据和验收目标的任务，按已有授权继续调查或修复。修复后 recheck 读取新源码、重核原触发及保护、逐项说明验收。仅文件变化或本轮无命中不能关闭。结果追加到新版本，保留“仍在 / 未核定 / 已修复 / 撤回”的区别；未覆盖的原问题留在待复查。
